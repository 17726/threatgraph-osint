# OpenCTI 架构借鉴分析

## 资料来源

1. OpenCTI 数据模型文档：https://docs.opencti.io/latest/usage/data-model/
2. OpenCTI GitHub：https://github.com/OpenCTI-Platform/opencti
3. OpenCTI 分析视图文档：https://docs.opencti.io/latest/usage/exploring-analysis/

## 项目定位

OpenCTI 是成熟的网络威胁情报平台，核心是基于 STIX 2.1 的知识图谱。它将威胁行为体、恶意软件、攻击技术、基础设施、报告等对象建模为图节点，将 `uses`、`targets`、`attributed-to` 等语义关系建模为图边，并通过连接器导入、富化和导出情报。

它的重点不是单次报告生成，而是长期维护一个可查询、可合并、可共享、可富化的 CTI 知识库。

## 与本项目架构对比

相同点：

1. 都以实体和关系为核心组织威胁情报。
2. 都需要区分实体、关系、来源、置信度和证据。
3. 都需要支持 ATT&CK 技术和攻击行为分析。
4. 都需要图谱查询和可视化。

OpenCTI 的优势：

1. STIX 2.1 语义完整，实体类型、关系类型、对象属性都有成熟标准。
2. 连接器生态成熟，适合长期接入外部威胁情报源。
3. 图谱、报告、推断关系、富化流程都在统一平台中闭环。
4. 更适合多团队协同和长期情报运营。

OpenCTI 相对本项目的不足：

1. 部署和学习成本高，不适合课程短周期直接复刻。
2. STIX 模型完整但复杂，P0 直接照搬会拖慢开发。
3. 它是通用 CTI 平台，不专门解决“LLM 从 OSINT 文本中抽取实体关系”的课程核心展示。

本项目当前架构的优势：

1. SQLite 作为唯一事实源，简单、可复现、易演示。
2. `graph.json` 可作为前端 mock 和演示兜底，风险低。
3. LLM 候选输出和 canonical graph 分层清楚，适合解释证据链。
4. 范围聚焦 3 个目标组织，更适合课程 MVP。

## 是否应该学习

应该学习 OpenCTI 的架构思想，但不应该复制它的平台形态。

建议学习：

1. STIX 风格的实体、关系、证据、来源和置信度建模。
2. 关系类型受控，避免 LLM 自由生成大量不可维护关系。
3. 连接器思想：外部来源先进入导入层，再进入事实源。
4. 图谱视图要能区分直接关系和推断关系。
5. 报告和分析结论要能回到图谱节点、关系和证据。

不建议学习：

1. P0 不实现完整 STIX 2.1。
2. P0 不做完整连接器管理平台。
3. P0 不做复杂权限、标记和组织隔离。
4. 不把 OpenCTI 当底层依赖，否则项目会变成“部署和二开 OpenCTI”，削弱自研系统表达。

## 阶段与优先级建议

### 优先级 P0

可吸收：

1. 保留当前 `entities`、`relations`、`evidence`、`confidence`、`source_count` 设计。
2. 固定实体类型和关系类型枚举。
3. 报告中明确区分“原文证据事实”和“系统推断结论”。
4. 前端图谱至少展示实体类型、关系类型、证据入口。

不放入 P0：

1. STIX bundle 导入导出。
2. 多组织权限和标记体系。
3. 大规模连接器生态。

### 优先级 P1

可吸收：

1. 关系类型校验，拒绝不合理的关系组合。
2. Neo4j 同步后支持多跳路径和关系解释。
3. 结构化报告章节引用 `evidence_ids`、`analysis_refs`、`graph_refs`。
4. 增量采集和导入运行状态展示。

### 优先级 P2

可吸收：

1. STIX 2.1 子集导入导出。
2. 与 OpenCTI 或 MISP 的兼容输出。
3. 更完整的情报标记、来源可信度和访问控制。
4. 类似连接器 SDK 的外部数据源扩展机制。

## 结论

OpenCTI 是本项目最重要的架构参考对象。我们应该借鉴它的知识图谱、STIX 风格建模、连接器和证据追溯思想，但要保持当前项目轻量可控。优先级 P0 只做“可解释的小型 CTI 图谱”，增强阶段再补图查询能力和标准化交换能力。
