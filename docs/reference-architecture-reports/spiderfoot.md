# SpiderFoot 架构借鉴分析

## 资料来源

1. SpiderFoot GitHub：https://github.com/smicallef/spiderfoot
2. Kali Linux SpiderFoot 工具说明：https://www.kali.org/tools/spiderfoot/

## 项目定位

SpiderFoot 是 OSINT 自动化工具，面向给定目标自动调用多种数据源和分析模块，收集域名、IP、邮箱、账号、漏洞、泄露信息等公开情报。它同时提供 Web UI 和命令行入口，适合做目标侦察和攻击面映射。

SpiderFoot 的核心价值是采集模块化和扫描任务管理，而不是威胁情报知识图谱建模。

## 与本项目架构对比

相同点：

1. 都需要从多种公开来源采集数据。
2. 都需要记录采集任务、来源、状态和结果。
3. 都需要把外部数据经过清洗后再进入系统内部模型。
4. 都需要保证采集失败不会污染正式数据。

SpiderFoot 的优势：

1. 模块化数据源设计成熟，容易扩展新来源。
2. 扫描任务模型清晰，适合记录状态、进度、结果和错误。
3. Web UI 和 CLI 双入口适合自动化和人工演示。
4. 面向目标的侦察流程直观。

SpiderFoot 相对本项目的不足：

1. 采集范围很广，但数据噪声较大。
2. 它偏技术对象侦察，不专注 APT 行为模式、事件时间线和知识图谱推理。
3. 依赖大量外部 API 时，课程演示环境不稳定。
4. 不解决 LLM 抽取、证据链归一化和智能报告生成。

本项目当前架构的优势：

1. `sources`、`collection_runs`、`collected_items`、`documents` 已经能承接轻量采集闭环。
2. P0 强调缓存和可复现，不强依赖实时采集。
3. 后续文档清洗、LLM 抽取、图谱构建和报告生成更贴合课程题目。

## 是否应该学习

应该学习 SpiderFoot 的采集器和任务运行模型，但不能把 P0 做成大型 OSINT 扫描器。

建议学习：

1. 采集器按类型抽象，例如 `local_json`、`http_page`、`rss_feed`。
2. 每次采集必须有运行记录、状态、错误、导入数量。
3. 采集条目先进入 `collected_items`，确认后再转入 `documents`。
4. 保留 Web API 和脚本两种触发方式。

不建议学习：

1. P0 不接入大量第三方 API。
2. 不做自动发现式攻击面扫描。
3. 不把采集范围扩展到过多目标类型。

## 阶段与优先级建议

### 优先级 P0

可吸收：

1. 实现最小三类采集器：`local_json`、`http_page`、`rss_feed`。
2. 完成 `POST /api/v1/collection-runs` 和 `GET /api/v1/collection-runs/{id}`。
3. 采集结果先写入 `collected_items`，再导入 `documents`。
4. 前端或 API 文档能展示最近采集状态。

不放入 P0：

1. 大量外部 OSINT API。
2. 自动递归爬取。
3. 扫描任务调度队列。

### 优先级 P1

可吸收：

1. 采集错误重试、超时、限速和去重。
2. 增量 checkpoint，避免重复导入同一 feed 条目。
3. 采集任务状态在前端展示。
4. 采集完成后可自动触发指定流水线步骤。

### 优先级 P2

可吸收：

1. 插件式采集器接口。
2. 更多外部 API 数据源。
3. 采集器健康检查和 API Key 管理。
4. 类似 SpiderFoot 的目标画像和攻击面扩展分析。

## 结论

SpiderFoot 对本项目最直接的价值是采集闭环设计。当前架构已经基本吸收了它的核心思想，但第一阶段应先坚持“本地文本入口 + 可复现缓存”，不要把课程项目做成不可控的大型爬虫平台。
