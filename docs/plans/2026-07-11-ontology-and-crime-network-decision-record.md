> 日期：2026-07-11

> 基线：`origin/main`，提交 `81f683e`

## 1. 设计目标

本轮设计服务于课程要求中的以下能力：

1. APT 攻击生命周期分析与 MITRE ATT&CK 映射。
2. 犯罪团伙组织结构、成员关联、资金流向和作案手法分析。
3. 按组织、时间、地区、攻击类型等维度查询知识图谱。
4. 关联路径追踪、智能推理、动态更新、图谱可视化和结构化报告。

设计原则：

1. 实体类型描述对象本身的语义类别，事件角色通过关系表达。
2. 黄金集只记录原文可证的事实，不记录依赖外部知识得到的补全结果。
3. 事实关系与推断关系分层保存，不能把推断结果直接混入正式事实。
4. P0 优先保证可查询、可验证、可展示，不建设完整通用本体。
5. 本次允许破坏性 Schema 升级，并迁移现有黄金集、示例和校验逻辑。
6. Schema 只能承载原文中存在的事实，不能弥补语料缺少成员、账户或资金流证据的问题。

## 2. 完整决策日志

本节按实际讨论顺序记录问题背景、候选方案、最终选择和选择原因。后续实现者不能只读取“最终选择”，还需要理解被排除方案的问题，避免在 Schema、Prompt 或前端中重新引入同一歧义。

### D0. 黄金集的职责边界

问题背景：黄金集用于和 LLM 抽取结果进行精确评测。如果把无关作者、外部知识补全或低置信待定关系混入黄金集，评测器会把这些内容视为正例，导致指标失真。

讨论过的方案：

1. 所有识别到的实体都进入 `entities（实体列表）`，再通过 `notes（备注）` 标明是否排除。
2. 只有与威胁事件相关的实体进入 `entities（实体列表）`；被排除对象只写入 `notes（备注）`。
3. 允许 QA 为黄金关系填写 `confidence（置信度）`，用低分表示待定关系。
4. 黄金集只保留确定正例，待定关系写入 `notes（备注）` 并进入复核。

最终选择：

1. 采用方案 2 和方案 4。
2. 文章作者、编辑、页面维护者等仅承担来源元信息角色时，不进入黄金实体列表。
3. 与威胁事件相关但暂时没有关系的实体仍应进入黄金实体列表。
4. 黄金关系不填写 `confidence（置信度）`；模型候选结果可以填写模型自评置信度。
5. `canonical_id（规范实体标识）` 和最终 `entity_id（实体标识）` 由后端归一化生成，不由 QA、data 或 LLM 手工填写。

选择原因：黄金集必须表示“完全正确且原文可证的答案”，而不是候选池或复核队列。`notes（备注）` 用于记录排除理由和待复核问题，不能改变实体列表作为正例集合的语义。

### D1. 黄金集与抽取结果的结构

问题背景：历史数据中 golden 和 extraction result 使用了不同字段名和不同嵌套结构，导致评测前还要做映射和扁平化转换。

讨论过的方案：

1. 保留两套结构，通过评测器做字段映射。
2. 统一关系字段和 chunk 结构，使两者可以直接比较。

最终选择：采用方案 2。

统一约束：

```text
关系字段：head_name（主体名称）
          head_type（主体类型）
          tail_name（客体名称）
          tail_type（客体类型）

数据结构：chunks[].entities（分块实体）
          chunks[].relations（分块关系）
```

`chunks（文本分块）` 由后端生成，data、QA 和 LLM 不手写；临时 mock 可以使用 `${doc_id}_c001`。

选择原因：统一结构可以减少无价值映射，降低评测器复杂度，并保证 schema-first 的契约能够直接约束黄金集和模型输出。

### D2. `TARGET（攻击目标类型）` 应当是实体类型还是关系角色

问题背景：同一个招商银行既是 `ORGANIZATION（组织）`，又可能在攻击事件中扮演目标；外交人员既是 `PERSON（人员）`，又可能是目标。当前 `TARGET（攻击目标类型）` 把对象类型和事件角色混在一起。

讨论过的方案：

1. 保留 `TARGET（攻击目标类型）`，用于泛指受害群体。
2. 删除 `TARGET（攻击目标类型）`，新增 `ENTITY_CLASS（实体类别）` 承载泛指对象。
3. 删除 `TARGET（攻击目标类型）`，泛指对象直接使用自身语义类型，目标角色只由 `TARGETS（攻击或针对）` 表达。

最终选择：采用方案 3。

选择原因：课程要求按组织、人员、地区和攻击类型进行多维度查询。泛指“金融机构”直接使用 `ORGANIZATION（组织）` 后，组织查询不会漏掉类别对象；`TARGETS（攻击或针对）` 则稳定表达它在具体事件中的角色。

### D3. 是否增加 `ENTITY_CLASS（实体类别）` 和 `class_of（所属基础类型）`

问题背景：具体对象和泛指类别存在层级，例如“招商银行”和“金融机构”。最初考虑使用专门类别节点解决同层混放问题。

讨论过的方案：

1. 所有泛指类别统一标为 `ENTITY_CLASS（实体类别）`。
2. 使用 `ENTITY_CLASS（实体类别） + class_of（所属基础类型）`，例如 `金融机构 -> ORGANIZATION（组织）`。
3. 不增加类别类型和字段，金融机构直接标为 `ORGANIZATION（组织）`，C2 服务器直接标为 `INFRASTRUCTURE（攻击基础设施）`。

方案 1 的问题：无法知道“金融机构”“外交人员”“军事设施”分别属于组织、人员还是地点，按组织查询和关系校验会变弱。

方案 2 的优点：可以严格校验类别基础类型；问题是所有泛指对象都需要额外字段，并会让同一语义类型分散到多个顶层类型。

最终选择：采用方案 3，不增加 `ENTITY_CLASS（实体类别）` 和 `class_of（所属基础类型）`。

选择原因：如果“C2 服务器”可以直接标为 `INFRASTRUCTURE（攻击基础设施）`，那么同一原则下“金融机构”也应直接标为 `ORGANIZATION（组织）`。实体类型负责语义分类，实例和类别层级在需要时由关系表达，更适合 P0 的查询和展示要求。

接受的代价：如果一个泛指节点没有任何 `INSTANCE_OF（是某类别的实例）` 入边，系统不会仅凭实体字段判断它是否为类别。P0 不把这一判断作为课程验收前置条件。

### D4. `PART_OF（是其组成部分）` 与 `INSTANCE_OF（是某类别的实例）`

问题背景：“招商银行属于金融机构”曾考虑使用已有 `PART_OF（是其组成部分）`，但这会混淆组成关系和分类关系。

讨论过的方案：

1. 复用 `PART_OF（是其组成部分）`。
2. 新增 `INSTANCE_OF（是某类别的实例）`。
3. 不记录具体实体和泛指类别之间的关系，只保留两条 `TARGETS（攻击或针对）`。

最终选择：新增 `INSTANCE_OF（是某类别的实例）`，但只标注原文可证的分类关系。

选择原因：`PART_OF（是其组成部分）` 表示部分与整体；具体银行不是“金融机构”这个类别的组成部件。`INSTANCE_OF（是某类别的实例）` 能保留混合表述中的明确层级，同时避免 QA 根据常识扩展原文。

### D5. `INDUSTRY（行业）` 与 `ORGANIZATION（组织）`

问题背景：“金融机构”和“金融业”容易被当成同一个对象，但前者是组织集合，后者是经济活动领域。

讨论过的方案：

1. 两者统一标为 `INDUSTRY（行业）`。
2. 两者统一为名称“金融”，弱化差异。
3. “金融机构”标为 `ORGANIZATION（组织）`，“金融业/金融服务业”标为 `INDUSTRY（行业）`。

最终选择：采用方案 3。

选择原因：这可以稳定回答“攻击了哪些组织”和“偏好哪些行业”两个不同查询。只有原文明示行业时才创建 `INDUSTRY（行业）`，不得从具体银行自行推导行业关系。

### D6. 攻击基础设施的粒度

问题背景：域名、IP、URL 和 C2 地址可以细分为多种技术对象，但 P0 数据量和查询需求尚不足以支撑完整可观测对象体系。

讨论过的方案：

1. 立即拆分 `DOMAIN（域名）`、`IP_ADDRESS（IP 地址）`、`URL（统一资源定位符）` 等类型。
2. 增加粗粒度 `INFRASTRUCTURE（攻击基础设施）` 统一承载。

最终选择：采用方案 2。

选择原因：先满足 C2、域名和 IP 的图谱查询与路径展示，避免在 P0 过早复制完整 STIX 可观测对象体系。后续有真实查询需求时再细分。

### D7. 地理实体的粒度

问题背景：课程明确要求国家、地区、军事基地、机场和冲突区域等地理实体，现有 `COUNTRY（国家）` 和 `REGION（地理区域）` 不能准确承载具体地点。

讨论过的方案：

1. 继续只用 `COUNTRY（国家）` 和 `REGION（地理区域）`。
2. 增加 `LOCATION（具体地点）`。

最终选择：采用方案 2。

边界：`COUNTRY（国家）` 表示国家；`REGION（地理区域）` 表示大范围地理或冲突区域；`LOCATION（具体地点）` 表示军事基地、机场、设施和具体地点。

### D8. 时间顺序与生命周期阶段

问题背景：课程明确要求事件时间序列和“侦察 -> 武器化 -> 投递 -> 利用 -> 安装 -> C2 -> 目标达成”的生命周期。现有 `LEADS_TO（导致或推进至）` 不能稳定替代纯时间先后关系。

讨论过的方案：

1. 继续使用 `LEADS_TO（导致或推进至）` 同时表达因果和时序。
2. 新增 `PRECEDES（发生在之前）` 表达纯时序，并保留 `LEADS_TO（导致或推进至）` 表达因果或行为推进。

最终选择：采用方案 2，并将 `attack_stage（攻击生命周期阶段）` 改为闭合枚举。

选择原因：前端时间线、路径查询和行为分析需要区分“先发生”和“导致”。生命周期阶段和 `tactic（MITRE ATT&CK 战术）` 也不是同一分类，必须分别保存。

### D9. 是否实现课程 3.b 犯罪团伙网络

问题背景：项目原有路线集中于 APT28、Lazarus 和 Kimsuky，但课程 3.b 明确要求犯罪团伙组织结构、成员关联、资金流向和作案手法分析。

讨论过的方案：

1. 最终演示只覆盖 APT 生命周期和目标偏好。
2. 同时承诺实现犯罪团伙组织结构与资金流向。

最终选择：采用方案 2。

选择原因：这是课程明确列出的核心模块，不应只通过报告文字声称覆盖。图谱中必须存在可查询、可追踪、有证据的成员和资金路径。

PR #22 的 QA 评审进一步指出：当前 `data/documents（标准文档目录）` 大部分材料集中在技术原理、工具、恶意软件、基础设施和攻击目标，不能稳定提供成员、账户和资金流证据。`apt28_001` 只描述国家利益导向和政府机构目标，不涉及资金流向。虽然部分 Lazarus、Kimsuky 相关材料提到加密货币窃取、勒索或洗钱，但通常仍缺少可构建账户路径的稳定账户标识、成员关系或转移方向。

因此，本决策拆成两个同时必须满足的门槛：

1. **数据门槛**：补充能够明确支持犯罪团伙成员和资金路径的 OSINT 文档，并完成人工证据核验。
2. **Schema 门槛**：在代表性文档确认后，冻结实体、关系和字段，使其能够无损承载真实证据。

只增加字段而不补充数据，不能满足课程 3.b；只补充数据而没有稳定 Schema，也不能形成可查询图谱。

数据处理策略已确认采用**增量补充**：保留现有 APT28、Lazarus 和 Kimsuky 文档，用于技术、工具、基础设施、攻击目标、生命周期和 MITRE ATT&CK 分析；另行搜索包含犯罪团伙成员、账户和资金路径证据的合格资料。不会因为现有文档不含资金流而将其删除，也不会要求全部数据同时覆盖课程的每一个分析维度。

### D10. 资金流向的建模粒度

问题背景：仅用主体之间的资金关系无法展示账户路径；完整交易模型又需要金额、币种、时间和交易标识等新结构。

讨论过的方案：

1. 主体级：团体或人员直接 `TRANSFERS_TO（向其转移资金）` 另一个主体。
2. 账户或钱包级：增加 `FINANCIAL_ACCOUNT（金融账户）`，通过控制关系和账户间资金方向建图。
3. 交易级：在账户模型之上结构化保存每笔交易的金额、币种、时间和交易标识。

最终选择：采用方案 2。

选择原因：账户级模型已经能演示团体控制钱包、钱包之间转移和资金路径追踪，足以对应课程“资金流向”；同时避免在缺少可靠逐笔交易数据时扩大 Schema。

明确不承诺：逐笔交易统计、余额计算、链上验证、洗钱模式识别和金额聚合。

生效前提：至少存在一份通过 QA 核验的文档，能够从原文中识别两个账户或钱包、明确的资金方向，以及至少一个账户与人员、团体或组织的控制或归属关系。若代表性语料无法满足此前提，不得通过推断或 mock 把账户级路径写入正式图谱，也不得在答辩中声称已实现账户级资金追踪。

### D11. 威胁主体模型尚未决策

问题背景：新增并列的 `CRIMINAL_GROUP（犯罪团伙）` 会与 `APT_GROUP（高级持续性威胁团体）` 重叠；成熟 CTI 模型通常将实际攻击者和根据行为聚类得到的入侵活动集合分开，或使用统一威胁主体加多值性质。

讨论过的方案：

1. 完整模型：`THREAT_ACTOR（威胁行为主体） + INTRUSION_SET（入侵活动集合）`。
2. 简化模型：统一为 `THREAT_GROUP（威胁团体）`，增加多值 `threat_group_types（威胁团体性质）`。
3. 并列类型：保留 `APT_GROUP（高级持续性威胁团体）` 并增加 `CRIMINAL_GROUP（犯罪团伙）`。

当前状态：方案 3 已明确不推荐；方案 1 与方案 2 交由后续负责人决策。详细取舍见第 7 节。

### D12. QA 对现有攻击来源模型的建议

问题背景：QA 认为当前三类主要数据都围绕 APT28、Lazarus 和 Kimsuky，`APT_GROUP（高级持续性威胁团体）` 与 `CAMPAIGN（攻击活动）` 已经能够表示现有攻击来源和活动，不需要为了课程展示引入新的威胁团体性质枚举。

QA 建议：

1. 将现有 APT 名称理解为证据有限的入侵活动集合，而不是百分之百确认的真实组织。
2. 保持现有 `APT_GROUP（高级持续性威胁团体）` 和 `CAMPAIGN（攻击活动）` 不变。
3. 不展示 `NATION_STATE（国家级行为主体）`、`CRIME_SYNDICATE（有组织犯罪集团）` 等对当前三个目标区分度较低的枚举。
4. 优先完善攻击目标方，不调整攻击来源方。

QA 根据现有公开信息给出的三组目标画像是：

1. Kimsuky：具有朝鲜国家背景，主要针对韩国政府及相关目标，偏向保密信息窃取。
2. Lazarus：具有朝鲜国家背景，目标包括金融机构和加密货币交易所，兼有经济利益和加密货币窃取活动。
3. APT28：具有俄罗斯国家背景，主要针对各国政府和军事部门，偏向保密信息窃取。

这些画像用于解释现有数据和报告展示差异，不能自动写入每篇文档的 golden。具体背景、动机和目标偏好仍必须由当前文档证据、后端归一化来源或明确的 enrichment（知识增强）记录支撑。

评审结论：

1. “现有数据不足”“字段不能替代数据”和“当前三个目标不需要团体性质筛选”成立，应写入范围约束。
2. “只完善攻击目标方”与已确认的课程 3.b 覆盖目标存在冲突。若团队坚持实现犯罪团伙组织与资金网络，就必须新增相应数据来源，并重新决定犯罪团伙在攻击来源侧的实体类型。
3. 在新犯罪团伙数据进入前，不应先实现 `threat_group_types（威胁团体性质）` 或修改现有 APT 展示。
4. `TOOL（工具）`、`MALWARE（恶意软件）` 和 `INFRASTRUCTURE（攻击基础设施）` 表示攻击资源，不等同于作案手法；作案手法继续由现有 `TECHNIQUE（攻击技术）` 和 `BEHAVIOR_PATTERN（行为模式）` 承载，无需为此新增实体字段。

## 3. 已确认的实体设计

### 3.1 删除 `TARGET（攻击目标类型）`

`TARGET（攻击目标类型）` 同时混合了实体类型和上下文角色，与 `PERSON（人员）`、`ORGANIZATION（组织）`、`INDUSTRY（行业）` 等类型存在重叠，因此删除。

是否为攻击目标统一通过 `TARGETS（攻击或针对）` 关系表达：

```text
APT28 TARGETS（攻击或针对） 招商银行
APT28 TARGETS（攻击或针对） 金融机构
```

其中：

```text
招商银行：ORGANIZATION（组织）
金融机构：ORGANIZATION（组织）
外交人员：PERSON（人员）
金融服务业：INDUSTRY（行业）
```

### 3.2 不增加 `ENTITY_CLASS（实体类别）` 和 `class_of（所属基础类型）`

当前阶段不单独区分具体实例和泛指类别。泛指对象直接使用对应语义类型：

| 文本对象 | 实体类型 |
| --- | --- |
| 招商银行 | `ORGANIZATION（组织）` |
| 金融机构 | `ORGANIZATION（组织）` |
| 张三 | `PERSON（人员）` |
| 外交人员 | `PERSON（人员）` |
| 某个 C2 IP | `INFRASTRUCTURE（攻击基础设施）` |
| C2 服务器 | `INFRASTRUCTURE（攻击基础设施）` |
| 某军事基地 | `LOCATION（具体地点）` |
| 军事设施 | `LOCATION（具体地点）` |

该设计保证按语义类型查询时不会漏掉泛指对象。例如，查询 `ORGANIZATION（组织）` 可以同时得到具体银行和“金融机构”类别。

### 3.3 增加 `INFRASTRUCTURE（攻击基础设施）`

P0 统一承载：

```text
域名
IP 地址
URL
C2 地址或服务器
其他直接用于攻击的技术基础设施
```

P0 不立即拆分为 `DOMAIN（域名）`、`IP_ADDRESS（IP 地址）`、`URL（统一资源定位符）` 等更细类型。

### 3.4 增加 `LOCATION（具体地点）`

地理类型边界：

| 实体类型 | 中文释义 | 示例 |
| --- | --- | --- |
| `COUNTRY（国家）` | 具有国家语义的地理实体 | 中国、法国 |
| `REGION（地理区域）` | 大范围地理或冲突区域 | 东欧、中东、某冲突区 |
| `LOCATION（具体地点）` | 军事基地、机场、设施或具体地点 | 某空军基地、某机场 |

### 3.5 增加 `FINANCIAL_ACCOUNT（金融账户）`

采用账户或钱包级资金网络，统一承载：

```text
银行账户
加密货币钱包
支付账户
其他可识别的资金收付账户
```

P0 不承诺逐笔交易模型，不结构化保存每笔交易的金额、币种、交易编号和余额。这些信息存在时仍需保留在原文证据中。

## 4. 已确认的关系设计

### 4.1 `INSTANCE_OF（是某类别的实例）`

用途：表达具体对象和泛指类别之间的分类关系。

```text
招商银行 INSTANCE_OF（是某类别的实例） 金融机构
```

约束：

1. 只有原文明示或语言上直接蕴含分类关系时才标注。
2. 不允许 QA 根据常识或外部知识自行补充。
3. 两端仍使用各自的语义实体类型，不增加 `ENTITY_CLASS（实体类别）`。
4. 后端可以根据 `INSTANCE_OF（是某类别的实例）` 的方向辅助判断实例和类别，但该判断是派生信息，不写入黄金集实体字段。

示例：

```text
原文：APT28 攻击了招商银行等金融机构。

APT28 TARGETS（攻击或针对） 招商银行
APT28 TARGETS（攻击或针对） 金融机构
招商银行 INSTANCE_OF（是某类别的实例） 金融机构
```

如果原文只写“APT28 攻击了招商银行”，不得补充上述 `INSTANCE_OF（是某类别的实例）` 关系。

### 4.2 `PART_OF（是其组成部分）`

`PART_OF（是其组成部分）` 只表示组成、隶属或整体与部分关系，不表示实例与类别关系。

```text
某下属组织 PART_OF（是其组成部分） 某总组织
某次事件 PART_OF（是其组成部分） 某攻击活动
```

错误示例：

```text
招商银行 PART_OF（是其组成部分） 金融机构
```

该场景应使用 `INSTANCE_OF（是某类别的实例）`。

### 4.3 增加 `PRECEDES（发生在之前）`

`PRECEDES（发生在之前）` 是有方向的时序关系，用于攻击步骤、事件或行为阶段排序：

```text
投递 PRECEDES（发生在之前） 利用
利用 PRECEDES（发生在之前） 安装
安装 PRECEDES（发生在之前） 命令与控制
```

`PRECEDES（发生在之前）` 只表达时间顺序；`LEADS_TO（导致或推进至）` 表达因果或行为推进，两者不能混用。

### 4.4 犯罪团伙组织和资金网络关系

已确认增加以下关系：

| 关系 | 中文释义 | 典型方向 |
| --- | --- | --- |
| `MEMBER_OF（是其成员）` | 人员或下级团体属于某团体或组织 | 人员 -> 团体或组织 |
| `CONTROLS（控制）` | 主体实际控制账户、钱包、组织或基础设施 | 主体 -> 被控制对象 |
| `TRANSFERS_TO（向其转移资金）` | 资金从一个账户或钱包流向另一个账户或钱包 | 金融账户 -> 金融账户 |

最小可演示路径：

```text
张三
  --MEMBER_OF（是其成员）--> 某犯罪团伙
  --间接关联--> 某作案手法

某犯罪团伙
  --CONTROLS（控制）--> Wallet A

Wallet A
  --TRANSFERS_TO（向其转移资金）--> Wallet B

某交易所
  --CONTROLS（控制）--> Wallet B
```

该模型支持组织成员查询、账户控制关系查询和资金路径追踪，但不承诺交易级统计。

## 5. 生命周期阶段枚举

`attack_stage（攻击生命周期阶段）` 使用闭合枚举，和 `tactic（MITRE ATT&CK 战术）` 分开保存。

| 枚举值 | 中文名称 | 说明 |
| --- | --- | --- |
| `RECONNAISSANCE（侦察）` | 侦察 | 收集目标、人员、系统和外部暴露面信息 |
| `WEAPONIZATION（武器化）` | 武器化 | 准备载荷、漏洞利用代码或攻击资源 |
| `DELIVERY（投递）` | 投递 | 将载荷或诱饵发送至目标 |
| `EXPLOITATION（利用）` | 利用 | 利用漏洞、配置或人员弱点获得执行能力 |

| `COMMAND_AND_CONTROL（命令与控制）` | 命令与控制 | 建立 C2 通道并控制受害系统 |
| `ACTIONS_ON_OBJECTIVES（目标达成）` | 目标达成 | 窃取、破坏、勒索、监控或其他最终目的 |
| `UNKNOWN（未知）` | 未知 | 证据不足，无法映射到具体阶段 |

MITRE ATT&CK 映射继续使用：

## 7. 待决策：威胁主体和入侵活动如何分层

这是当前唯一尚未收敛的核心本体决策，交由后续负责人继续评审。

### 7.1 方案 A：完整双层模型

实体类型：

| 类型 | 中文名称 | 含义 |
| --- | --- | --- |
| `THREAT_ACTOR（威胁行为主体）` | 威胁行为主体 | 真实存在、具有恶意意图的个人、团体或组织 |
| `INTRUSION_SET（入侵活动集合）` | 入侵活动集合 | 根据共同恶意软件、基础设施、TTP 和目标聚合出的一组攻击活动，不要求已知真实主体 |

关系示例：

```text
APT28
  INTRUSION_SET（入侵活动集合）
    --ATTRIBUTED_TO（归因于）-->
  某真实机构
  THREAT_ACTOR（威胁行为主体）
```

优点：

1. 最接近 STIX 2.1 和 OpenCTI 的设计。
2. 能区分“观察到的攻击活动集合”和“真实攻击者”。
3. 归因不确定时不会把厂商命名的活动集合误当成已确认组织。

代价：

1. 现有 `APT_GROUP（高级持续性威胁团体）` 数据需要重新研判和迁移。
2. QA 必须判断每个名称表示真实主体还是活动集合。
3. Prompt、关系矩阵、归一化和前端展示复杂度明显增加。

### 7.2 方案 B：简化威胁团体模型

统一实体类型：

```text
THREAT_GROUP（威胁团体）
```

使用多值字段 `threat_group_types（威胁团体性质）`：

| 枚举值 | 中文名称 | 释义 |
| --- | --- | --- |
| `NATION_STATE（国家级行为主体）` | 国家级行为主体 | 由国家控制、支持或代表国家利益行动 |
| `CRIME_SYNDICATE（有组织犯罪集团）` | 有组织犯罪集团 | 以规模化犯罪和经济获利为主要目标 |
| `ACTIVIST（激进主义团体）` | 激进主义团体 | 出于政治、社会或意识形态目的发动攻击 |
| `TERRORIST（恐怖主义团体）` | 恐怖主义团体 | 以制造恐慌或推进极端政治目标为目的 |
| `PRIVATE_SECTOR（私营机构行为主体）` | 私营机构行为主体 | 企业或其他私营机构支持的攻击主体 |
| `UNKNOWN（未知类型）` | 未知类型 | 证据不足，无法判断性质 |

该字段允许多选，因为国家背景、犯罪获利、意识形态等性质可能同时存在。

优点：

1. 适合课程 P0，标注和展示成本较低。
2. 可以统一承载 APT 团体和犯罪团伙。
3. 主实体类型稳定，团体性质不必强行互斥。

代价：

1. 把真实攻击组织和厂商根据行为聚合出的入侵活动集合合并处理。
2. 归因语义不如方案 A 严谨。
3. 后续若兼容 STIX 2.1，需要增加映射或再次拆分。

### 7.3 不推荐方案：并列类型

```text
APT_GROUP（高级持续性威胁团体）
CRIMINAL_GROUP（犯罪团伙）
```

该方案不推荐。一个团体可能同时具有国家背景和犯罪获利行为，两个实体类型无法保证互斥，会重复当前 `TARGET（攻击目标类型）` 的分类问题。

### 7.4 QA 建议方案：现有 APT 来源模型暂不调整

继续使用：

```text
APT_GROUP（高级持续性威胁团体）
CAMPAIGN（攻击活动）
```

并在文档中明确：`APT_GROUP（高级持续性威胁团体）` 是项目对安全厂商命名活动集合的简化表达，不代表已经百分之百确认背后的真实组织。

该方案最符合当前三个 APT 目标和现有语料，能够避免无展示价值的枚举字段；但它没有回答新增犯罪团伙语料应使用什么实体类型。因此，如果课程 3.b 继续作为实现目标，该方案只能作为现有 APT 数据的兼容策略，不能单独构成完整犯罪网络方案。

候选枚举：

| 枚举值 | 中文名称 |
| --- | --- |
| `BANK_ACCOUNT（银行账户）` | 银行或其他金融机构账户 |
| `CRYPTO_WALLET（加密货币钱包）` | 链上钱包或加密货币地址 |
| `PAYMENT_ACCOUNT（支付账户）` | 第三方支付或在线支付账户 |
| `OTHER（其他金融账户）` | 不属于以上类型的账户 |
| `UNKNOWN（未知账户类型）` | 原文未说明或无法判断 |

需要决定：该字段是否进入 golden、是否必填，以及钱包地址和账户名称分别如何填写 `name（名称）` 和 `aliases（别名）`。

#### Q5. 实体子类型如何落库？

当前 `entities（规范实体表）` 没有实体类型专属字段。候选方案：

1. 在 `entities（规范实体表）` 增加通用 `attributes_json（扩展属性）`。
2. 直接增加 `threat_group_types_json（威胁团体性质）`、`threat_actor_roles_json（威胁主体角色）`、`financial_account_type（金融账户类型）` 等列。
3. 新建 `threat_group_profiles（威胁团体画像表）` 和 `financial_accounts（金融账户表）` 等类型专属表。

需要从 Schema 约束、查询复杂度、迁移成本和后续 STIX/MISP 兼容性四方面给出选择理由。

#### Q6. 犯罪组织结构需要哪些关系？

```text

```

仍需决定是否增加：


#### Q7. 是否重命名业务字段 `target_group（目标团体）`？

如果采用 `THREAT_ACTOR（威胁行为主体） + INTRUSION_SET（入侵活动集合）`，现有 `target_group（目标团体）` 可能过度绑定 APT 团体概念。

候选方案：

1. 保留 `target_group（目标团体）` 作为项目业务分组键，不等同于实体类型。
2. 改为 `subject_id（分析对象标识）` 或 `analysis_subject（分析对象）`。

需要评估目录结构、API、SQLite、报告和现有数据迁移影响。

#### Q8. 是否区分资金性质？已决策

QA 指出“资金流向”可能表示犯罪所得，也可能表示攻击活动经费；国家背景 APT 的主要目的还可能是情报获取，不能默认存在赃款。

候选方案：

1. `TRANSFERS_TO（向其转移资金）` 保持中性，只表达原文明确的转移方向；资金性质保留在证据和报告描述中。
2. 增加可选字段 `fund_flow_purpose（资金流目的）`，仅在原文明示时填写。

若增加字段，候选枚举为：

| 枚举值 | 中文名称 |
| --- | --- |
| `CRIMINAL_PROCEEDS（犯罪所得）` | 犯罪、盗窃或勒索所得资金 |
| `OPERATIONAL_FUNDING（活动经费）` | 支持攻击、人员或基础设施运营的经费 |
| `EXTORTION_PAYMENT（勒索付款）` | 受害者支付的勒索资金 |
| `LAUNDERING（洗钱流转）` | 为掩盖来源或去向而进行的资金流转 |
| `UNKNOWN（未知资金性质）` | 原文没有说明资金性质 |

最终选择：采用方案 1。P0 不新增 `fund_flow_purpose（资金流目的）`，`TRANSFERS_TO（向其转移资金）` 只表达原文明确的资金方向。犯罪所得、活动经费、勒索付款和洗钱等性质保留在证据及报告文字中，不作为结构化查询维度。

选择原因：课程要求资金流向，但没有要求按资金性质查询；现有数据也不能稳定区分赃款和活动经费。保持关系中性可以避免把攻击动机误当成资金事实。

#### Q9. 数据门槛未满足时如何处理课程承诺？已决策

候选方案：

1. 补充数据后再实现并验收账户级资金网络。
2. 将账户级资金网络降为设计能力，不在答辩中声称已实现。
3. 改为课程允许的其他分析场景，并在报告中说明未覆盖犯罪资金网络。

最终选择：采用方案 1，由 data 组配合补充合格资料后再实现和验收账户级资金网络。

如果最终仍无法满足数据门槛，必须显式重新决策，不能用空字段、mock 或 LLM 推断替代真实证据。
